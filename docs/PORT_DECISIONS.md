# Перенос бота в сайт — принятые решения

Контекст: сайт становится самостоятельной реализацией CHM Breaker (свой движок, свои
аккаунты, без зависимости от Telegram-бота во время работы). План переноса и
спецификации подсистем лежат вне репозитория (сессия переноса); здесь — решения,
которые влияют на код.

### D5 / M13b — запуск автотрейда на сайте

`services/autotrade/index.js` (`createAutoTrade`) — порт `auto_trade.execute_auto_trade` со всем, что
он вызывает; движок-воркер подключает его как `deps.autoTrade` планировщика **только при
`AUTOTRADE_ENABLED=1`** (по умолчанию выключено: деплой сам торговлю не включает). `AUTOTRADE_EXCHANGES`
— список бирж (по умолчанию `bybit,bingx`); для биржи вне списка сканеры получают «нет ключей»
(ни ордера, ни записи в БД — как у пользователя без ключа). Источники того, что бот читал из своих
таблиц: строка `users` = `trader_settings` + `users.telegram_username` + passphrase OKX из
`exchange_keys`; ключ — `exchange_keys` (метка `default`, иначе самый новый — тот же, что Mini App
показывает подключённым), расшифровка только в памяти, в лог не пишется; ADMIN_IDS = `users.is_admin`;
`mutation_log` → `audit_log`; `notification_queue` не переносится (потерянное уведомление не
переотправляется — уведомления сайта и так хранятся в `notifications`). Неразбираемый
`DAILY_MAX_LOSS_R` не даёт автотрейду стартовать (бот падает при импорте config.py), а не выключает
circuit breaker молча.

Сверка с ботом: `backend/tests/autotrade/core` — 113 векторов `execute_auto_trade` (CPython 3.11,
фейковые трейдеры, виртуальное время; прогоняются и через `createExecutor`, и через `createAutoTrade`),
36 сценариев лестницы partial TP на уровне HTTP-запросов, `%`/`str.format` и `config.py` из CPython 3.11.
Воспроизводятся (а не исправляются) причуды бота: три гейта (`hour_of_day_levels`, `min_quality`,
`trending_only`) заменяют результат на `{ok:false, executed:false, skip}`; `_price_multiplier` для OKX
ищет `bybit_price_multiplier` → WARNING и 1.0 на каждый вызов; `ai_filter_json` не сохраняется
(`database.db_exec` нет); строка риска в сообщении — только при тёплом кэше баланса; сделка,
найденная reconcile после таймаута, остаётся в `PLACING`; предупреждение circuit breaker — один раз на
процесс; ветка устаревания WS мертва (HTTP-цена всегда); в partial TP запрос средней цены входа и
финальная проверка позиции Bybit идут на live-хост (`kwargs["bybit_demo"]` никогда не задан);
`fixed_amount` для OKX запрашивает баланс без passphrase; `fixed_amount` обходит `max_risk_pct`;
BingX partial TP без `positionSide`, Binance — успех при `code >= 0`; `cross_direction_msg` кладётся в
результат, но ни один сканер его не отправляет. Исправлены только D6: `executed=false` при отказе биржи,
`fixed_amount` — процент баланса (в настройках 0,5…3 %).

Один процесс: автотрейд живёт в воркере движка, а движок рассчитан на один процесс приложения
(`backend/services/engine/README.md`: `PassengerMaxInstances 1` / `PassengerMinInstances 1`). Два процесса —
два движка и **два ордера на один сигнал** (ключ идемпотентности `auto_trade` — со случайным uuid, реестр — в памяти процесса); общий
лизинг движка между процессами — M19. До него `AUTOTRADE_ENABLED=1` только при одном процессе.
Фоновые задачи сделок бота (БУ-монитор с переносом стопа после TP1 и записью итога, reconcile,
SL-верификатор, детектор аномалий, sweeper) — веха M15; до неё у позиций сайта их нет (итог сделки не
записывается, через 3 дня ghost cleanup бота ставит открытой строке `SKIP`), поэтому `AUTOTRADE_ENABLED=1`
в проде — только после M15.

Golden-тесты: `backend/tests/golden` (фикстуры сгенерированы Python-кодом бота, см. там README).

## D15 — ключ с правом вывода не принимается

Одна реализация — `backend/services/autotrade/keyPermissions.js` — за обоими путями добавления ключа:
`POST /api/app/exchange/keys` (`services/exchangeKeysService.js`, после `test_connection` бота, 20 с) и
`POST /api/exchanges/keys` страницы аккаунта (`routes/exchanges.js`, до `exchangeService.addKey`). Одно
чтение прав у биржи (8 с); запрос подписывает собственный код трейдера — байт в байт то, что строит
подпись бота для этого эндпоинта:

| Биржа | Запрос | Право вывода |
|---|---|---|
| Bybit | `GET /v5/user/query-api` на хосте ключа (live или demo) | любое имя в `result.permissions` с `withdraw` (Wallet → `Withdraw`); группа не списком / имя не строкой → неизвестно |
| BingX | `GET /openApi/v1/account/apiPermissions` | код `5` в `data.permissions` (или строка `"5"` / имя с `withdraw`); другие типы элементов → неизвестно |
| Binance | `GET https://api.binance.com/sapi/v1/account/apiRestrictions` (HMAC, `X-MBX-APIKEY`), только HTTP 200 | `enableWithdrawals: true` → вывод, `false` → ок, иное → неизвестно |
| OKX | `GET /api/v5/account/config` (demo → `x-simulated-trading: 1`) | `withdraw` в `data[0].perm` (код `"0"` и непустая строка, иначе неизвестно) |

Всё, что не явное «вывода нет», — «неизвестно» → ключ не сохраняется. Ответы: `/api/app` —
`{"ok": false, "error": "withdraw_permission" | "permission_unknown", "message": …}`; `/api/exchanges` —
400 `KEY_CAN_WITHDRAW` / 503 `KEY_PERMISSIONS_UNVERIFIED`; тексты одни (ru/en, язык пользователя). Ничего
не пишется (ни ключ, ни `trade_exchange`, ни сброс счётчика ошибок авторизации); в лог — биржа и
вердикт, без ключа, секрета, passphrase и подписи. Testnet-ключи Binance/BingX: у тестовых сетей нет
этих эндпоинтов → «неизвестно» → отказ. В тестах (NODE_ENV=test / vitest) транспорт по умолчанию
соединений не открывает. Тесты: `backend/tests/autotrade/ops/d15.test.js` (запрос против подписи
бота, враждебные формы ответа), `backend/tests/autotrade/core/keyPermissions.test.js` (вердикты,
оба пути, «одна реализация»).

Эндпоинты и поля сверены с описаниями API в ccxt 4.5.47 (офлайн, `node_modules/ccxt`): BingX
`account/v1` private GET `account/apiPermissions`, Bybit `v5/user/query-api` (`result.permissions`, группа
`Wallet`), Binance sapi `account/apiRestrictions` (`enableWithdrawals`), OKX `account/config` (пример
`"perm": "read_only,withdraw,trade"`). Записанные ответы всех четырёх бирж (вывод есть / нет / сбой
эндпоинта) через оба маршрута — `backend/tests/autotrade/safety/security.test.js`.

**Открыто:** формы ответов — из документации и ccxt (живой биржи в песочнице нет) — перед включением
каждой биржи ответ эндпоинта проверяется на живом ключе (с правом вывода и без).

Удаление ключа (`DELETE /api/app/exchange/keys`, `DELETE /api/exchanges/keys/:id`) действительно удаляет
строку `exchange_keys`; если у биржи не осталось ключа — `trader_settings.auto_trade = 0` (как бот после
удаления ключа); сессия pybit этого ключа и кэш баланса пользователя сбрасываются в процессе, который
обработал запрос (сессии pybit в других потоках живут до своего TTL 12 ч, но ключ из БД уже не
читается — новых ордеров с ним нет). Чужой id → 404. Sentry: `utils/sentry.js` `scrubEvent` вычищает
ключи/секреты/passphrase/подписи (`api_key`, `api_secret`, `passphrase`, `signature`, `sign`, …) из тела,
query, заголовков бирж (`X-BAPI-*`, `X-BX-APIKEY`, `X-MBX-APIKEY`, `OK-ACCESS-*`), extra, contexts и
локальных переменных кадров стека.

## D16 — кнопки сделки только там, где их показал бы бот

В боте кнопки «✅ Открыть сделку», «🎯 50% / 💰 100% / 🛡 SL→BE» есть только на карточке сигнала в чате
владельца, а после нажатия «Открыть» карточка редактируется без кнопок. `exec_trade` бота владельца не
проверяет (до него нельзя дотянуться иначе); на сайте маршрут `POST /api/app/trades/{id}/exec` доступен
для любого id, поэтому `backend/routes/appTrade.js` до любой работы проверяет: сделка принадлежит
пользователю из JWT и (для exec / qc half / full / force / be) кнопка с этим callback ещё есть в
`signal_card_json.actions`; иначе 404 `{"ok": false, "error": "not_found"}` — без запросов к бирже и
записей. Прогресс (`GET …/progress`) проверяет только владельца. Обработчики дальше — один в один с
ботом (`services/autotrade/confirmMode.js`, `quickClose.js`), под замком сделки (exec) и замком
пользователя (`workers/tradeOpsWorker.js`).

Очередь trade-ops (`workers/tradeOpsWorker.js`) строит трейдеров с теми же хуками, что движок
(`createTradeOpsRegistry`: killswitch, plan gate, trade events, сброс Bybit-сессии при 10003/10004): в боте
`place_trade` сам проверяет killswitch, поэтому «Открыть сделку» при `HALTED_*` не уходит на биржу
(ответ трейдера `killswitch_halted: <state>`). Перед обработчиком exec — переключатели D5: при
`AUTOTRADE_ENABLED≠1` или бирже вне `AUTOTRADE_EXCHANGES` ответ «⛔ Автоторговля … не включена — сделка
не открыта» без правки карточки и без запросов (закрытие и SL→BE остаются доступны).

## D17 — биржа сделки и позиции OKX

Бот не пишет `trades.exchange` (быстрое закрытие всегда читает Bybit), а `positions` для OKX
распаковывает 2-кортеж `get_dashboard` в три имени (позиции OKX всегда «недоступны»). Сайт: биржа
размещённого ордера пишется в `signal_trades.exchange` (авто — `executeAutoTrade.js` `d17.recordExchange`,
confirm — `confirmMode.js`); позиции OKX — `get_positions` + `get_open_orders` (`appTrade.js`,
`D17_SITE.okxPositions`). Режим бота (`{recordExchange: false}`, `{okxPositions: false}`) прогоняют реплеи
`backend/tests/autotrade/ops/tradeOpsReplay.test.js` и `units.test.js`. **Нужно подтверждение владельца.**

Быстрое закрытие больше не отличие сайта: ошибки исправлены в самом боте (ветка
`claude/funny-edison-529rg1`, 2026-10) и перенесены на сайт один к одному, фикстуры перегенерированы
исправленным ботом:

* `[QC-SIDE-FIX]` — `close_position` получает направление позиции (LONG/SHORT), а не сторону закрытия
  (раньше: Bybit — reduce-only «Buy» для LONG, 110017; BingX/Binance — `positionSide=SELL`, отказ биржи;
  OKX — `posSide=short`); размер берётся у позиции направления сделки (hedge-счёт держит обе);
  сделка без LONG/SHORT отклоняется до запросов; 50 % на OKX — рыночный ордер противоположной
  стороны на тот же `posSide` (`close_position_partial`), раньше — `TypeError`;
* `[OKX-CLOSE-CLEANUP]` — после закрытия на OKX SL/TP снимаются, только если закрытие прошло или OKX
  подтвердил, что позиции этой стороны нет; при живой позиции другой стороны (hedge) снимаются только
  ордера своей стороны. Раньше снималось всё по символу даже после неудачного закрытия — позиция
  оставалась без стопа;
* `[BINANCE-CLOSE-ONEWAY]` — на one-way счёте (`-4061`) закрытие повторяется с `positionSide=BOTH` +
  `reduceOnly`; ответ без `orderId` и без кода ошибки — не успех;
* `[BINGX-DUP-VERIFY]` — `101204` у BingX это «недостаточно маржи»: отказ считается повтором уже
  принятого `clientOrderId`, только если биржа так и пишет или ордер с этим `clientOrderId` находится
  запросом. Раньше `101204` давал `ok` без позиции (сделка OPEN, которой нет на бирже);
* `[EXEC-STALE-GUARD]` — кнопка «✅ Открыть сделку» не открывает сигнал, который трекер уже закрыл
  (стадия не `''`/`ENTRY`: SL, TP1–3, BE, MISSED, EXPIRED) или который старше горизонта трекера
  (`SIGNAL_TRACKER_MAX_AGE_H`, 72 ч): ответ «⚠️ Сигнал устарел или уже отработал. Сделка не открыта.»
  без запросов к бирже. Раньше между EXPIRED трекера и чисткой «призраков» (3 дня) ордер уходил;
* `[OKX-LOT-CONTRACTS]` — размер OKX считается целыми лотами в контрактах (`lotSz`/`minSz` — в
  контрактах, 1 контракт = `ctVal` монет): меньше `minSz` без opt-in boost — пропуск (low notional),
  с boost — минимальный ордер биржи; доли TP2/TP3 — целыми лотами, нога меньше `minSz` уходит в TP1;
  `qty` в ответе = отправленный `sz × ctVal`; ноги partial TP / `place_sl_tp_for_position` меньше лота
  не отправляются. Раньше BTC открывался только целыми контрактами (размер меньше одного добивался до
  1 контракта — риск ×2…×16 на малом счёте), а у DOGE уходил `sz "0"`;
* `[BINGX-PTP-POSSIDE]` — частичный TP на BingX: сторона `SELL`/`BUY` и `positionSide` позиции (раньше
  «Sell»/«Buy» без `positionSide`: на hedge-счёте BingX подставляет LONG, и TP шорта открыл бы лонг);
  `109400` (one-way) → повтор с `positionSide=BOTH` + `reduceOnly`;
* `[OKX-PTP-POSSIDE]` — частичный TP на OKX: `posSide` позиции (на long/short-счёте обязателен — без него
  лимитный TP отклонялся всегда) и цена кратно шагу tickSz, к входу;
* `[OKX-SLTP-REPLACE]` — стоп OKX на всю позицию (`place_sl_tp_for_position` и перенос SL / в безубыток):
  алго-ордера читаются с `ordType=conditional`; стоп на всю позицию (`closeFraction "1"`, у OKX один на
  позицию) уже на той же цене — ничего, на другой — `amend-algos`, нет — новый (раньше `sz "0"` — не размер
  OKX); остальные стопы снимаются только после этого; TP — целыми лотами, старые TP снимаются только когда
  встали все новые; ордера другой стороны hedge-счёта не трогаются;
* `[OKX-ENTRY-TIMEOUT]` + `[OKX-CLORDID-ALNUM]` — вход OKX с `clOrdId` (только буквы и цифры, как требует
  OKX; раньше `sl_…`/`tp1_…` с подчёркиванием — 51000, атомарный вход всегда уходил в legacy). Ответ на
  вход потерян или OKX сообщил о дубле `clOrdId` → ордер ищется по `clOrdId` (пауза 1 с, «нет» — после
  двух ответов 51603): найден — сделка привязана (без прикреплённого SL — стоп ставится отдельно; раньше
  SKIP при живой позиции с SL), нет — обычная ошибка, неизвестно — таймаут, и авто-трейд без повтора
  входа сверяет позицию (`[OKX-NO-BLIND-RETRY]`); 50004 (таймаут шлюза OKX) — тоже потерянный ответ
  (`[OKX-ENTRY-50004]`); найденный вход с прикреплённым TP1 без SL — только SL, без второго TP1;
* `[OKX-TIMEOUT-UNKNOWN]` — таймаут-сверка OKX: позиция не прочиталась → спрашивается сам вход по
  `clOrdId`: исполнился → привязка, нет → SKIP без отмены ордеров символа (вход OKX всегда market), не
  ясно → ни отмены, ни SKIP (`order_id` = `clOrdId`, алерт, «OKX не ответила, открылась ли сделка»);
  раньше нечитаемая позиция = «нет позиции» → отмена прикреплённых SL/TP1 живой позиции + SKIP;
* `[OKX-TP-CROSSED]` — TP, цена которого уже пройдена (51279 / 51277), не неудача: его лоты уходят
  следующим целям, старые TP снимаются (раньше после исполнения TP1 новые TP2/TP3 ложились поверх
  старых); `[OKX-NO-FILTERS]` — без фильтров инструмента стопы OKX не трогаются (шаг цены 0.01 увёл бы
  стоп дешёвой монеты за вход);
* `[OKX-SLV-ALGO]` — проверка стопа видит алго-стопы OKX (раньше `/orders-pending` их не показывал, и бот
  каждые 3 мин переставлял SL/TP и слал ложное «ПОЗИЦИЯ БЕЗ SL!»; на сайте — вместе с M15);
* `[BINANCE-BATCH-OFF]` — пакетный вход Binance (`batchOrders`) выключен: в проде он не срабатывал ни разу
  (подпись ломалась, -1022) и не атомарен (элементы пакета исполняются независимо; «вход принят, SL
  отклонён» дал бы позицию без стопа). Работает последовательный путь вход → SL → TP;
* `[PTP-TP-PLACED]` — лестница partial TP, которую ставит фон после открытия (а также main TP фолбэка и
  лестница таймаут-сверки), встала на бирже → `tp_placed=1`. Раньше флаг оставался 0, и BE-монитор снимал
  эту лестницу (BingX/Binance — вместе со старым SL, если новый не встал) и ставил вторую. Binance — только
  при живой позиции (висящий LIMIT-вход: условные TP принимаются, а BE отменил бы вход); OKX — только если
  сделка открылась со стопом (ответ `place_trade` теперь несёт `sl_placed`); фолбэк BingX/Binance — только
  если встал и новый SL; таймаут-сверка ждёт свой SL-фолбэк;
* `[EXEC-QTY-TP]` — кнопка «✅ Открыть сделку» сохраняет размер позиции (`qty`) и `tp_placed` из ответа биржи,
  как авто-трейд (раньше — ни того, ни другого: BE-монитор снимал выставленную лестницу TP, а BU после
  частичного TP и PnL-фолбэк не работали); Binance — `tp_placed=1` только при живой позиции стороны сделки;
* `[POS-READ-STRICT]` — `getPositions(..., {strict: true, errOut})` у всех четырёх бирж: неудачное чтение
  (код ошибки, таймаут, мусор в ответе) → `null` + текст ошибки, а не `[]` «позиций нет». Нужен сверке и
  sweeper'у M15 (раньше ошибка чтения → отмена SL/TP живой позиции и ORPHAN); без `strict` — как раньше;
* `[BE-OKX]` — `okx.cancelTpOrders(k, s, symbol, direction, pp)`: снимает только тейки одной стороны (лимиты
  закрывающей стороны своей `posSide`, net — reduce-only; алго с `tpTriggerPx` без `slTriggerPx`); стопы,
  входы и другая сторона hedge-счёта остаются. Для BE-монитора M15 (раньше `cancel_all_orders` снимал и SL);
* `[BYBIT-DELIST-TTL]` — авто-блэклист Bybit (три ответа 10001 / 170214) живёт 24 ч от последней ошибки и
  сбрасывается успешным входом; раньше — до перезапуска процесса (BE-монитор писал SKIP живым сделкам);
* `[GHOST-LIVE-TRADES]` — чистка «призраков» по возрасту (3 дня) больше не трогает строки с ордером на
  бирже: живую позицию ведут BE-монитор и сверка, SKIP обрывал её сопровождение.

Всё перечисленное — сначала исправлено в боте (ветка `claude/funny-edison-529rg1`), эталоны сайта
перегенерированы из исправленного бота и сравниваются побайтно (биржи, wire, core, trade-ops, e2e,
статистика). Остальные исправления пакета (BE-монитор, сверка, детектор аномалий, один BE-цикл) сайт
переносит вместе с фоновыми циклами M15.

## D18 — деньги при сбоях (таймаут, повтор, падение процесса, остановка)

Инвентарь всех путей, которые отправляют, меняют, отменяют или закрывают ордер (`MONEY_PATHS` в
`backend/tests/autotrade/safety/moneyPaths.test.js`; тест падает, если в коде появился новый вызов
ордерного метода трейдера вне таблицы): авто-вход `execute_auto_trade` (+ его SL/partial TP, LIMIT-guard
отмены), confirm «Открыть сделку», быстрое закрытие 50 % / 100 %, SL→BE. Каждый путь проверен на четырёх
фейковых биржах (`safety/world.js`: настоящая БД сайта, подписи проверяются, транспорт с отказами
«потерян до/после биржи», «соединение не установлено», «ответ оборван», «завис») на: обычный проход,
таймаут после того, как биржа ордер приняла, повтор, падение процесса посреди размещения и рестарт,
двойное нажатие / параллельные запросы, падение воркера trade-ops, killswitch и гейты риска (fail-closed).

Где бот может открыть вторую позицию на один сигнал или оставить позицию без SL / без учёта, сайт
по умолчанию (переключатели `d18`, режим бота `{inflightGuard: false, reconcileFailedRetry: false}`
прогоняют реплеи `tests/autotrade/core` — все 113 векторов проходят в обоих
режимах):

- **Незавершённое размещение** (`inflightGuard`): процесс, упавший между записью строки `PLACING` и
  записью order id, оставляет строку без `order_id`; бот такую строку не видит (`db_has_open_trade_for_symbol`
  требует order id), и тот же сигнал, найденный после рестарта, открывает вторую позицию. Сайт считает
  строку `PLACING` без order id того же пользователя и символа моложе 30 мин (`STUCK_PLACING_MAX_AGE_S`)
  открытой сделкой: авто — `SKIP` `d18_inflight_placement` (`[D18-INFLIGHT]`), confirm — «уже открыта»
  (`dup_symbol`). Через 30 мин строка больше не блокирует (позиция к тому времени — забота reconcile M15).
- **Повторный вызов для той же сделки** (`inflightGuard`): если `trade_id` уже размещён, бот находит «открытую
  сделку символа» — свою же — и пишет ей `SKIP`; сайт оставляет строку как есть (`[D18-DUP-SELF]`).
- **OKX без слепого повтора** — больше не отличие: с 2026-10 так делает сам бот (`[OKX-NO-BLIND-RETRY]`,
  вход OKX несёт `clOrdId`, потерянный ответ ищется по нему — `[OKX-ENTRY-TIMEOUT]`), сайт перенёс один в
  один. Bybit, BingX и Binance повторяют один раз с тем же client order id, как бот.
- **Отказ или дубликат повтора после таймаута** (`reconcileFailedRetry`): Binance отвечает на повтор
  `-4116` (client id уже есть) — бот пишет `SKIP` при живой позиции без учёта; BingX дубликат — бот
  отвечает `ok` без SL. Сайт в обоих случаях делает reconcile первой попытки (`[D18-RETRY-RECONCILE]`):
  позиция найдена → строка с order id и SL, не найдена → `SKIP`.
- **Карточка confirm до ордера**: бот редактирует карточку («⏳ Открываю сделку...», без кнопок) до
  `place_trade`; сайт делает то же и сразу пишет `signal_card_json` (ошибка записи → ордер не уходит), так что
  повторное нажатие после падения воркера — 404, а не второй ордер.
- **Остановка движка**: бот при остановке отменяет задачи (размещение может оборваться посреди). Сайт:
  `beginShutdown` — новые размещения не начинаются (`SKIP` `d18_shutting_down`, confirm-карточка всё равно
  отправляется), начатые получают до 15 с (`AUTOTRADE_DRAIN_MS`), потом реестр идемпотентности
  сохраняется; `server.js` даёт воркеру 18 с.

Остаётся как у бота (закреплено тестами): после таймаута, найденного reconcile, строка остаётся `PLACING`;
повтор partial TP (OKX/BingX) не идемпотентен, но ордера reduce-only; confirm exec не перепроверяет
SL-серию, circuit breaker и потолок риска в момент нажатия; чтения позиций Bybit/OKX бота глотают ошибки
(«не прочитано» = «пусто»), поэтому при недоступной бирже reconcile не находит позицию.

Тесты: `backend/tests/autotrade/safety/moneyPaths.test.js` (пути, отказы, рестарт, остановка, замки,
fail-closed, IDOR), `security.test.js` (обход гейтов параметрами, killswitch-админка, D15, удаление ключей,
утечки ключей в логи/ответы/БД/Sentry, авторизация, инъекции).

## Killswitch в админке (PLAN §1.5)

Команды бота `/ks_status`, `/halt <причина>`, `/halt_all <причина> CONFIRM`, `/resume <токен>` — маршруты
админки (`backend/routes/admin.js`, только администратор): `GET /api/admin/engine/killswitch` (состояние,
без значения токена), `POST …/killswitch/halt {reason}` (409 при уже `HALTED_NEW`, ответ с токеном
возобновления), `POST …/killswitch/halt-all {reason, confirm: "CONFIRM"}` (иначе 400 `confirm_required`),
`POST …/killswitch/resume {token}` (400 `token_required`, 403 `invalid_token`). Каждое изменение пишется в
`audit_log` с id администратора (в боте — `mutation_log`). Состояние то же, что читают движок и trade-ops:
при `HALTED_*` ни авто-вход, ни «Открыть сделку» не уходят на биржу; ошибка чтения состояния — тоже стоп
(fail-closed, как бот).

## Проводная сверка с ботом (M13b, wire diff)

`backend/tests/autotrade/wire` (README там же): бот сам (`execute_auto_trade`, Mini App-хендлеры ключей и

трейдеров сначала пробрасывает его (`pyCompat.rethrowCancelled`); `bybit_call` — `wait_for(to_thread)`
со своим таймаутом и строкой лога бота; `wait_for` маршрутов (проверка ключа 20 с, позиции 8 с, размер
позиции в quick close 10 с) отменяет работу — после таймаута ни одного лишнего запроса; процессные и
trade-ops трейдеры работают в этой же среде (`productionOverrides`). Закреплены причуды бота: пакет
Binance переподписывается yarl после подписи (-1022 → по одному ордеру), BingX batch 100001 в проде,
OKX fixed_amount без passphrase, OKX «таймаут после приёма» → SKIP при открытой позиции, BingX 101204 и
Binance -4015 как «дубль = успех», BingX 80001 → «Неверный API ключ.», OKX `sz "0.0"`,
`executed=True` при отказе биржи (в режиме бота `d6`; сайт по D6 отвечает false), проверка ключа OKX с
неверным секретом проходит (D15 его отклоняет). Сверка идёт в режиме бота (`d6` / `d17` выключены).

## Продуктовый слой «как Veles, но лучше» (D13) — правила по умолчанию

Полная концепция: `docs/PRODUCT_CONCEPT.md` (исследование Veles, конкуренты, боли пользователей,

| # | Вопрос | Решение |
|---|---|---|
| Q1 | Сколько ботов у пользователя | Слоты: до 3 ботов, по одному на стратегию (движок не меняется); N ботов — на этапе конструктора |
| Q2 | «За результат» (D14) | 20% чистого реализованного PnL ботов за календарный месяц, с переносом убытка (high-water mark), потолок $69 = цена Pro; в минусовый месяц $0; постоплата; при неоплате — пауза новых входов, позиции не закрываются. Числа в конфиге |
| Q3 | Что входит в «За результат» | Боты на бирже без ограничений Pro; ручные сигналы и анализ — в квотах Free; демо 14 дней на бота |
| Q4 | Награда за онбординг-чеклист | 7 дней Pro за весь чеклист, без денег на баланс |
| Q5 | Публичная лента на лендинге | Задержка 60 минут, уровни скрыты, стопы показываются наравне с тейками |
| Q6 | Боты сообщества на витрине | Позже, после юридической проверки; сейчас только витрина команды |
| Q7 | Термин | «Бот»; «стратегия» = Уровни / SMC / Объём + MA внутри бота |
| Q8 | Старт витрины | Витринные аккаунты запускаются заранее; публичный реестр всех кандидатов с датой запуска |

**Правила честности (обязательны для витрины, лендинга, SEO-страниц):** бумажный трек трекера
подписывается «трек сигналов (бумажный)», не «LIVE»; реальные сделки копий — «биржа»; бэктест геномов
не называется «вне выборки» (по нему шёл отбор) — для сравнения используется только отложенный период;
«walk-forward» не используется, вместо него «проверка стабильности по 4 периодам»; параметры витринного бота
заморожены, правка = новая версия со своим треком; на витрину — после 30 закрытых сигналов **и** 30 дней;
снятые боты уходят в архив; доходность всегда рядом с просадкой и числом сделок, R в % — только с оговоркой
о риске; комиссии вычитаются по модели бэктестера с подписью «оценка»; шкала риска пересчитывается под риск

лендинге без цели по умолчанию; калькулятор оплаты с прибылью 0 по умолчанию.

### d4 — качество входа VOLUME

- [VOL-MIN-VOLUME] Пол объёма сетапа (bounce/ribbon/golden ≥ ×1.5, env VOLUME_MIN_SETUP_VOL_MULT, 0 — выкл) — одна реализация в strategies/volume/quality.js; применяется при каждом создании VolumeConfig (как __post_init__) и в _fix; golden ≥ max(1.0, пол).
